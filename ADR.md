# InsureFlow Architecture Decision Record

## Status

Accepted

## Context

InsureFlow is being restarted as a broker-led insurance orchestration platform.

The updated system must support:

- simple customer insurance purchase flow
- admin-only broker registration
- generated broker API keys
- Main Backend and Provider Backend separation
- transaction tracking in both backends
- insurance-specific details linked to transaction
- provider-owned quote generation
- provider-owned payment session creation
- provider-owned policy issuance
- customer dashboard and admin dashboard

The customer should not select between brokers. Broker onboarding is an operational/admin process.

## Decision 1: Split Main Backend And Provider Backend

Use two backend services:

```txt
Main Backend
Provider Backend
```

Main Backend owns:

```txt
customer authentication
admin authentication
applications
main transactions
insurance_details
normalized quotes
quote selection
add-on selection
dashboard
admin operations
support tickets
audit logs
provider sync events
```

Provider Backend owns:

```txt
provider registration
broker API-key registration
insurance plans
add-ons
provider transactions
provider quotes
payment session creation
payment verification
receipt generation
policy generation
policy document generation
webhook retries
```

## Decision 2: Admin-Only Broker Registration

Customers will not choose a broker in the UI.

Broker registration is done only by an InsureFlow admin.

Flow:

```txt
Admin logs in
→ Admin verifies 2FA
→ Admin receives ADMIN JWT
→ Admin registers broker
→ Main Backend validates ADMIN JWT
→ Main Backend forwards request to Provider Backend
→ Provider Backend generates broker API key
→ Provider Backend stores API key hash
→ Plain API key is returned once
```

Broker registration should store:

```txt
broker_code
broker_name
api_key_hash
callback_url
webhook_url
status
created_by_admin
created_at
updated_at
last_key_rotated_at
```

Plain API key must not be stored.

Example API key:

```txt
brk_live_<secure_random_token>
```

## Decision 3: API Key Generation

Provider Backend generates broker API keys.

Example:

```py
import secrets
import hashlib

def generate_broker_api_key() -> str:
    return f"brk_live_{secrets.token_urlsafe(32)}"

def hash_api_key(api_key: str) -> str:
    return hashlib.sha256(api_key.encode("utf-8")).hexdigest()
```

Only this is stored:

```txt
api_key_hash
```

Plain API key is shown only once to admin.

## Decision 4: Transaction Model In Both Backends

Both backends should have transaction models, but they should not duplicate the same responsibility.

Main Backend:

```txt
transactions
```

Purpose:

```txt
Main customer/business journey source of truth.
```

Provider Backend:

```txt
provider_transactions
```

Purpose:

```txt
Provider-side execution tracker for quote generation, payment, and policy issuance.
```

Provider transaction links to Main transaction using:

```txt
main_transaction_reference
```

## Decision 5: Insurance Details Linked To Transaction

Insurance-specific fields should not be stored directly inside the transaction model.

Create:

```txt
insurance_details
```

Link:

```txt
transaction_reference
```

Stores:

```txt
insurance_type
coverage_amount
tenure
sum_insured
insured_members
health_details
vehicle_details
travel_details
home_details
life_details
nominee_details
```

Reason:

Different insurance types require different fields. Keeping them in `insurance_details` avoids making the transaction model too large and sparse.

## Decision 6: Provider Backend Owns Quote Generation

Quotes are generated by Provider Backend.

Flow:

```txt
Frontend
→ Main Backend
→ Provider Backend
→ Main Backend
→ Frontend
```

Main Backend coordinates the request and stores normalized quotes.

Provider Backend calculates quote options using:

```txt
insurance plans
add-ons
insurance details
risk rules
premium calculation
```

## Decision 7: Provider Backend Owns Payment Session Creation

Main Backend must not create the payment URL or gateway order.

Provider Backend creates:

```txt
Razorpay order
payment session
payment reference
checkout metadata
```

Main Backend only forwards payment session data to frontend.

## Decision 8: Policy Generated Only After Payment Success

Policy generation happens only after verified payment success.

Flow:

```txt
Payment success verified
→ Provider Backend marks payment success
→ Provider Backend generates receipt
→ Provider Backend generates policy
→ Provider Backend generates policy document
→ Provider Backend syncs status to Main Backend
```

## Consequences

Positive:

- customer flow stays simple
- broker credentials are not exposed to users
- payment secrets stay in Provider Backend
- policy issuance happens only after verified payment
- Main Backend remains clean orchestration layer
- Provider Backend owns provider execution
- transaction lifecycle is traceable

Tradeoffs:

- requires reliable sync between Main Backend and Provider Backend
- requires careful status management
- requires broker API key rotation and secure storage
- requires `insurance_details` and `provider_transactions` to be kept linked with transactions

## Final Architecture Summary

```txt
Customer
→ Frontend
→ Main Backend
→ Provider Backend
→ Payment Gateway
→ Provider Backend
→ Main Backend
→ Customer Dashboard
```

Admin broker registration:

```txt
Admin Frontend
→ Main Backend admin API
→ Provider Backend broker registry
```

Main Backend models:

```txt
users
otp_tokens
applications
transactions
insurance_details
quotes
tickets
audit_logs
webhook_events
```

Provider Backend models:

```txt
providers
broker_registry
insurance_plans
addons
provider_transactions
provider_quotes
payments
policies
webhook_retries
```
